# Ariadne 与直接 Codex：同模型简历配对评测

日期：2026-10-14。评测源码基线 `23e51fcff21eb0903c1643656015c9e053b0efb2`；两端均固定 `gpt-6.1-sol/high`。用户选择仅使用合成资料。本阶段评测与建议完成后，由用户决定产品如何修改。

## 判断

**本次结果不足以证明 Ariadne 整体比直接 Codex 更好用。** 完整资料、当前更正、长文尾部、翻译及续写的主要事实，两端均能保持；Ariadne 的依据记录和版本门禁已具备实际运行证据，但这批样本没有证明它减少了事实错误或人工操作。格式适应存在明确差距：只换双栏模板时，直接 Codex 完成了两页 PDF，Ariadne 明确说明当前单栏限制，没有交付新文件。

建议先补齐**参考模板的版式表达与实际 PDF 导出能力，并将格式不支持与缺事实分开处理**。保留第一阶段的逐条依据、完整上下文、来源身份、版本冲突与人工保存边界。无需为这一结果重写整个架构，也不能将更多 agent 或更多模型调用本身当作改进。

下列“可交付”仅指本次合成任务的事实、要求和文件检查，不是本人履历核验、所有招聘系统兼容或录用效果保证。下一阶段产品改动尚未实施。

## 同条件比较的方法

正式组为 `runs/main-v3/C01–C09`，覆盖两个合成身份、一个选定职位及相关分支，每类每端执行一次，不在失败后挑选重生成结果。前八类来自上一阶段提出的任务，第九类检查必要身份缺失时正确补问。

两端获得相同的当前要求、完整已结构化资料、实际用户补充原话、选定职位和两页视觉模板。C03/C04/C05/C07 分别从各端真实 C01 完整稿分支，不能拿另一端或另一个分支替代。C06 实际传入约 155 KB 完整上下文，尾部研究事实及历史撤回都在；C07 重新建立会话并读回各自已有完整稿和模板。C09 请求明确指出身份缺失，验证适当补问，未测试自动发现隐含缺失。

Ariadne 执行当前生产上下文构建、原领域语义路由、简历生成、同型号独立事实审核及实际浏览器 PDF 导出；不以测试替身生成结论，也不强制路由或弱化校验。事务测试使用隔离合成数据库，另有真实浏览器持久化验证。

直接 Codex 使用标准原生 CLI `exec --ignore-user-config`，启用正常本地文件、shell、图片和 PDF 工具，固定同一型号、high 与 workspace-write。不注入 Ariadne 的语义指令、依据台账、审核流程或强制返回 schema。Ariadne 在复用模板的 C03/C05/C07 第一步领域路由没有传图，后续生成与审核各传完整两页；新模板任务每步均传两页，C08 无模板。不能把所有 23 次请求都说成包含两页图片。两端禁止外部搜索、应用、MCP、记忆及生成时再分派 agent；现有 Ariadne 登录由 CLI 正常解析，未读取或复制凭据。这是**原生 Codex CLI 的成品基准**，不是桌面 Codex 界面的全部操作体验。

共同输入已是结构化来源陈述，不比较原始 PDF 导入或理解质量；C07 是完整稿恢复与连续改稿，不比较原生 Codex 的正常 thread/resume 交互成本。

三位独立 agent 分别审核方法、事实和成品；事实与成品评审仅接触随机 X/Y 的共同事实、当轮聊天、各自前稿、真实 PDF 与全部 26 张页图，独立锁定后再交叉复核。主 agent 另核对真实请求、回执、来源与文档版本。**来源隐藏不完全**：C02/X、C03/Y、C04/Y、C06/Y、C07/Y 聊天保留 native 文件路径，PDF Producer 与排版也可能泄露生成端；这是独立评审，不能称完全双盲或独立人类验收。评判采用具体通过/失败标准，避免用不透明总分替代错误说明；方法参照 [OpenAI 评测指南](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。

7 类明确要求 PDF 的任务，共产生 13 份本轮 PDF：Ariadne 6 份，直接 Codex 7 份。数量仅表示文件存在，不等于内容和版式全部通过；C08/C09 的正确无文件行为单独评价。已生成的 PDF 都是两页，无“仅供参考”、品牌水印或内部审阅注记，实际中英文字可提取，页图检查无裁切或重叠。双栏文件在 pdfplumber 按横向行排序时会交错，pypdf 的内容顺序可读；未测试所有 ATS。

两位评审独立锁定后交叉核对，主要裁决无分歧，原独立报告保持不变。事实评审未发现旧指标复活、SQL 能力编造、模板事实替用或翻译增强职责。部分输出没有显式重述“仅负责研究/同事部署”，但也没有将部署归给本人；记非阻断的表达精度观察。直接 Codex 的 C08/C09 聊天还出现内部来源标签/材料路径，属用户表达问题。两位评审均认为 13 份现有 PDF 在本次合成要求范围内可交付；唯一明确未完成是 C04 Ariadne。细节覆盖、模板结构变体与虚构分开记录，不能用“没有编造”代替检查全部要求。

## 架构与实际操作的结论

Ariadne 的 ResumeTask 实际保留完整稿、逐条来源、模板身份和版本；九类任务核查没有改写 Candidate/Job 确认资料、来源或记忆。失败/澄清时旧稿仍在，未把旧稿冒充新交付。独立审核与身份/CAS 门禁体现为可追溯的流程；这批两端都没有重大事实错误，因而**没有实证优势可以归因于额外审核调用**。

当前约束把成品压缩为 A4 单栏 blocks，模型即使理解两栏要求也无法在产品内表达和导出。这是工具/契约的能力边界。C04 最终被记录为 `NEEDS_FACTS`，但缺的是版式能力，不是用户事实；继续要求补资料不能解决。建议显式区分格式不支持、缺事实、运行失败和正常待审核，并保留模板、请求、前稿与原回执。

真实 egolite 浏览器验证了 Ariadne C01 的 IndexedDB 保存、页面重开、ResumeTask/模板身份恢复以及下载 PDF 与原文件字节完全一致。隔离页同时显示 Local/provider=null 文案与失败提示；此证据只支持恢复与下载，不支持“正常已连模型的整页零错误体验”或重开后 GUI 继续编辑已验收。自动化脚本也没有测量人类点击数、重复说明时间或桌面 Codex 操作量。因此“减少重复操作、更好用”仍需真实用户流程对照。

C08 两端都能提出有证据的练习建议。尚未提交练习产物、形成新证据并实际复评，不能判断谁更能提升能力；本阶段也没有评测职位搜索、招聘信息质量或自动投递。

## 耗时、用量和失败记录

| 项目 | Ariadne | 直接 Codex |
|---|---:|---:|
| 正式执行形态 | 23 次 Provider 请求 | 9 个 agent turn，包含模型与工具多步执行 |
| 全部九类模型/agent 执行时间总和 | 919.856 秒 | 1103.172 秒 |
| 九类执行时间中位数 | 109.754 秒 | 115.035 秒 |
| 运行报告的 tokens | prompt+completion 共 323,988 | input 1,077,630；output 26,303 |
| 缓存输入信息 | 归一化回执未提供 | cached input 786,560 |

原生 agent turn 不等于一次模型推理请求，不能把 23 对 9 当作调用成本比。原生 input 包含大量缓存，两端 usage 字段和缓存暴露程度不同；没有账单或可对比费用证据，不换算美元或宣称节省百分比。Ariadne 6 次 PDF 渲染各为 39–128 ms，另行记录。

时间是实验负载下的真实模型/agent 执行，不含人类操作或 C02 后处理恢复等待；两端并行、部分 case 也重叠，且 Ariadne C04 未完成 PDF 的较短执行被计入。**不能把总和或中位数当作成功交付更快的证明**；逐 case 时间与原始 usage 留在本机 `metrics.json`。

两个准备组完整保留且不进入正式质量比较：第一组误关闭 native code-mode host，第二组手动 App Server 配置未提供正常文件工具，后者 Ariadne 另遇一次原传输超时。修正评测工具能力后，两端均从新 C01 开始，正式组零重新生成/挑选。

正式 C02 Ariadne 三次模型请求成功且产出 READY，但评测 harness 错读 Job 的回复字段，后处理抛错。修复本地评测投影，复用原模型结果、原不可变上下文，重新执行实际校验与事务保存后导出；没有新模型请求、正文修改或校验放宽。原失败和恢复回执保留。该成品可评，但此 case **不算无人工修复的端到端成功**。这不是产品源码修复，也不将 harness 问题暗记为模型失败。

## 建议及等待用户决定的范围

| 顺序 | 建议 | 具体验收 |
|---|---|---|
| 1 | 扩充简历版式契约和渲染器，先支持本次单栏/双栏参考 | 同一完整资料和前稿，仅换版式；两页、左右栏、栏目顺序、日期及事实全部保持；中文/英文可提取，无水印、注记、重叠或漏尾。不能实现时准确说明原因，保留原件与旧稿。 |
| 2 | 区分缺事实、格式不支持和运行失败 | 本次 C04 不再进入缺事实状态；缺身份仍适当补问。页面、聊天、任务状态和实际文件一致；不能把旧文件显示为完成本轮格式。 |
| 3 | 用真实用户流程验证更好用，再决定能力闭环 | 在用户授权的资料和同一模型下比较完整投递流程，记录重复说明、必要补问、实际操作和文件合格情况；练习须提交真实产物、新证据并完成复评，计划不算已具备能力。 |

优先完成前两项即可直接针对本次明确差距；第三项是后续验证/产品选择，不在本阶段启动。仍复用当前来源、分域、Working/Proposal、人工保存与资格机制；不扩展 Provider、通用 Agent 平台或自动投递。
